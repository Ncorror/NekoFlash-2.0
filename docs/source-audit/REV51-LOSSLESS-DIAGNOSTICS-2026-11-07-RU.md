# REV51 — полная диагностическая история в тестовых сборках

Дата: 7 ноября 2026. Задача: [#50](https://github.com/Ncorror/NekoFlash-2.0/issues/50).

## Зачем

На физическом HOST POCO F7 последний архив REV48 содержал `log-2026-11-07-13-51-12.txt` и `trace-2026-11-07-13-51-12.txt`, начинавшиеся в 13:53:45 без обязательных заголовков, хотя summary утверждал, что сессия началась в 13:51:12 и фиксировал более ранние события. Ротация по 2/8 MiB не срабатывала (файлы малы). Само происхождение пропуска не установлено. **Нельзя выдавать форматно корректный ZIP за доказательство полной истории.**

## Кодовые изменения REV51

- `DeviceViewModel.logInternal`: убрано пропускание повторных сообщений в 1500 мс. Отдельный ADB Shell stdout/stderr и транспортные буферы не меняются. Все вызовы `log(...)` сохраняются отдельно. Подавление новых дублей отключено; исторический счётчик `duplicatesSuppressed` остаётся в JSON для обратной совместимости.
- `DiagnosticLogStore`: сегменты и по-прежнему сохраняются без автоматической очистки; размер 2/8 MiB — **граница одного файла, а не ограничение полной истории**. Никакого нового ограничения на общий размер сессии/файлов не вводилось. При каждом добавлении проверяется существование и ожидаемая длина активного сегмента. Раньше `File.appendBytes()` мог **молча создать заново удалённый извне файл**, после чего в нём отсутствовал заголовок и начало событий. Теперь это явная ошибка хранения, не ложное продолжение журнала. Это правдоподобный механизм старого симптома, но он **не доказан** для сессии 13:51.
- `DiagnosticEvidenceArchive.writeDetailed`: копирует исходные байты диагностических файлов в ZIP потоково с SHA-256 каждого файла. Добавлен `EXPORT-MANIFEST.txt`: имена, длины, хэши, явный статус. Обнаруживает отсутствие исходного заголовка основного `log-YYYY-MM-DD-HH-mm-ss.txt` / `trace-*.txt`, изменение размера/mtime во время копирования, отказ сканирования папки и попытку выхода по символьной ссылке. В случае полного отсутствия найденных файлов добавляет `NO_LOGS.txt`. Неклассифицированные произвольные файлы в каталогах диагностики по-прежнему не копируются, чтобы не утянуть случайный firmware IMG/APK; известные префиксы диагностических файлов не ограничены расширением.
- `MainActivity.exportDiagnosticArchive`: перед экспортом сохраняет последний checkpoint; успех показывается только при согласованном снимке. При предупреждениях ZIP сохраняется для разбора, но интерфейс объявляет его **неполным или непроверенным**; исходные журналы не удаляются.
- `DiagnosticEvidenceArchiveTest`: SHA-256, чтение байт, 400 повторов, ротация в несколько сегментов, отсутствие начала сессии, отказ от молчаливого пересоздания удалённого активного файла, обнаружение внешнего обрезания, пустой экспорт и несколько путей хранения.

## Границы фикса и что осталось

1. В манифесте «CONSISTENT_SNAPSHOT» означает, что прочитанные файловые снимки не поменяли длину/mtime во время чтения, **не** что подтверждена полнота событий с запуска процесса. Подлинность исходного журнала архив сам доказать не может.
2. По-прежнему необходимо найти, **куда делась первая часть** конкретного журнала 13:51:12: сравнить оригинал в папке NekoFlash со старым экспортом, проверить сдвиг workspace, создание/обрезание файла внешними программами и события storage error. Нельзя считать #50 закрытой из-за одних только контрольных сумм.
3. После успешного CI — испытание на POCO F7 с длительной ADB-сессией, повторяющимися событиями и сменой USB-режимов, **без дополнительной записи разделов**. Сравнить SHA-256 исходных файлов и всех элементов ZIP. Никакие реальные бинарные логи и идентификаторы устройств не публиковать в открытый GitHub.
4. Динамически изменяющиеся файлы могут поменяться без изменения длины/mtime; для строгой временной консистентности понадобится транзакционный snapshot/маркер версии. Этот этап не включён в REV51. UI намеренно не обещает абсолютной полноты.
5. Буфер видимых строк терминала ограничен ради стабильности UI, но исходная история на диске сохраняется. Не увеличивать память пропорционально всему stdout; использовать потоковое хранение.
6. Разбор Sideload/OrangeFox и проверка способа получения финального результата ведутся отдельно в #47. Не объявлять установку успешной из-за 100% передачи.

**Статус:** код и автоматические тесты отдельной ветки; физическая приёмка не выполнена. `main` не изменён.


## Верификация архива на Android / Termux без повторной прошивки

В тестовой ветке находится \`scripts/verify_diagnostic_zip.py\` (Python 3, стандартная библиотека, **только чтение**). Команда сравнивает SHA-256 каждого содержимого ZIP с EXPORT-MANIFEST.txt, контролирует количество и имена элементов, а при явно указанной доступной папке исходников — сравнивает с оригиналами. Ничего не распаковывает, не удаляет и никуда не отправляет. Код возврата: 0 = согласованный снимок, 2 = старый формат/неполный или неподтверждённый экспорт, 1 = ошибка целостности или несовпадение с оригиналами.

Установка инструмента в Termux (Python должен быть установлен): 
~~~sh
curl -fL -o verify_diagnostic_zip.py \
  'https://raw.githubusercontent.com/Ncorror/NekoFlash-2.0/fix/rev51-lossless-diagnostics/scripts/verify_diagnostic_zip.py'
python verify_diagnostic_zip.py /sdcard/Download/NekoFlash-diagnostics-НОВЫЙ.zip
~~~

Если в ZIP оригинальные общедоступные журналы находятся под префиксом \`logs/3/\`, можно дополнительно сверить их с доступной папкой (номер определяется по манифесту, **не угадать**):
~~~sh
python verify_diagnostic_zip.py /sdcard/Download/NekoFlash-diagnostics-НОВЫЙ.zip \
  --source-root '3=/sdcard/Download/NekoFlash/logs'
~~~

Вторая команда проверяет соответствие только тому набору исходных файлов, который доступен по указанному пути. Приватные каталоги APK Android могут быть недоступны Termux без специальных разрешений; **не пытаться обходить sandbox**. Старую сборку без манифеста скрипт отметит как LEGACY, даже если все CRC внутри ZIP проходят. Не путать это с настоящей целостностью исходных событий.

Для аппаратной приёмки сохранить старые логи, экспортировать ZIP из новой REV51 APK, запустить проверку и прислать результат без чувствительных исходных данных. Повторно прошивать recovery/system/vendor/super ради этого не надо.
