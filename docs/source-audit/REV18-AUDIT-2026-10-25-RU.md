# NekoFlash 2.0 — аудит legacy-основы и исправления REV18

Дата: 25 октября 2026. Исходная ревизия: `455bc364dfb58fead73d2ef956ab70b51eb48af1` (REV17).
Код исправлений: `b74bfcdf37fb073fd48a23b321856fd3c918b2d6` (основной патч `8e93c8b382cfb34d771fcd3fc008512dc12aae5f`).
Рабочая ветка: `work/rev18-audit-ui-20261024`. [Draft PR #4](https://github.com/Ncorror/NekoFlash-2.0/pull/4).

## Вывод

Проект продолжает исходный NekoFlash. USB-движок не переписан с нуля, MiAccountClient и MiUnlockClient совпадают с архивом побайтно. При этом утверждение «нового кода вообще не было» неточно: предыдущие ревизии добавили адаптеры источников SAF, очередь, PTY-ввод, политики проверки и тесты. REV18 добавляет небольшие вспомогательные классы для исправления конкретных дефектов старых операций.

Состояние — техническая альфа. Ориентировочная инженерная оценка выполнения полного согласованного плана: **65–70%**. Это не измеренное покрытие тестами и не вероятность успешной прошивки. До стабильного выпуска остаются существенные задачи: семантика CLI, привязка результатов к попытке, жизненный цикл исполнителя, большие образы и испытания USB на устройстве.

## Границы исправлений

- SYNC v1 STAT содержит 32-битный размер. Проверка REV18 не является полной 64-битной проверкой или хешированием; нулевой/неизвестный размер оставлен допустимым для виртуальных файлов. Нужен STAT-v2 и отдельная политика изменяющихся файлов.
- Совпадение размера файла очереди не обнаруживает замену содержимого на другой файл того же размера. Между проверкой и открытием остаётся окно изменения источника. Следующий шаг — стабильный открытый FD на весь шаг.
- Проверка canonical path не устраняет все гонки при внешней подмене symlink во время записи. Для полной защиты нужны операции относительно открытого каталога.
- `FilePublication.publishNew` сериализует публикации внутри приложения. Поведение при конкурентной записи другого приложения и атомарная замена на Android emulated storage требуют проверки.
- Исправлено декодирование захваченного shell-результата; потоковый вывод терминала ещё не получил полноценный инкрементальный UTF-8 decoder.
- Legacy shell без exit-кода не может достоверно подтвердить успех команды. Новый завершающий NUL-маркер защищает конкретно получение списка для pull, а не все legacy shell-команды.
- Capture больших каталогов/логов всё ещё накапливает результат в памяти. Это отдельная задача потокового разбора.
- Показатели скорости и потребления памяти на телефоне не измерялись; заявления об ускорении в процентах отсутствуют.

## Что сохранено из согласованных правил

Порядок очереди и замена записи только для точного target; остановка после первой ошибки; ручной reboot; отсутствие GUI-пересортировки и ограничения на 32 элемента; default HOST CLI и PTY только для явного `adb shell`; полные диагностические файлы без автоматического удаления; single USB owner, URB drain/poison, отсутствие слепого повторения записи; production package `ru.forum.adbfastboottool`, DEV `.dev`, `/sdcard/Download/NekoFlash`.

Ограничения размера одного DATA, честная ошибка после оборванной передачи и запрет удалить открытый источник — условия корректной операции. Для больших файлов нужны поддержанные способы передачи, а не удаление этих проверок.

## Первичные источники для проверки Fastboot

- [AOSP constants.h](https://android.googlesource.com/platform/system/core/+/refs/heads/main/fastboot/constants.h): команда `reboot-fastboot`, современные размеры команд/ответов.
- [AOSP Fastboot protocol](https://android.googlesource.com/platform/system/core/+/refs/heads/main/fastboot/README.md): DATA и последовательность передачи.
- [AOSP fastboot.cpp](https://android.googlesource.com/platform/system/core/+/refs/heads/main/fastboot/fastboot.cpp): host-обработка format/wipe/fetch.

Аудит не утверждает, что найдены все возможные ошибки. Он фиксирует воспроизводимые статические дефекты, внесённые исправления, пройденные автоматические проверки и отдельно — непроверенные аппаратные сценарии.
