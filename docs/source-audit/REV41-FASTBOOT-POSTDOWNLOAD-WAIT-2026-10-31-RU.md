# REV41 — безопасное ожидание финального ответа Fastboot DATA

Дата: 2026-10-31. База: DEV `4d069eff9f0b0bdcef5eda980ee8066f12590405` после REV40.

## Найдено по исходникам

`FastbootProtocol.downloadAndRun` использовал `readUntilFinal(30000)` сразу
после успешного `download:...` и DATA. Это один USB IN вызов с длинным
ожиданием каждого пакета; при нескольких `INFO` бюджет ожидания фактически
возобновлялся, а отмена могла реагировать лишь после блокирующего чтения.

## Исправлено

Используем уже имеющийся `readUntilFinalWithRetry` с короткими 2-секундными
чтениями и общим 30-секундным сроком для этого этапа.
При завершении по `OKAY` команда после скачивания идёт как прежде;
`FAIL` обрабатывается по прежней ветке. При исчерпании времени сессия
помечается BROKEN, без повторной отправки Fastboot-команды/блока DATA.

`stageAndOemUnlock`, `flashPartitionDetailedInternal`, транспорт UsbRequest,
NativeUsbfs, sync bulk, файл, подпись и на-дисковая диагностика НЕ изменены.

## Регрессионные гарантии

Тест `FastbootPostDownloadWaitPolicyTest` фиксирует бюджет 30с и краткость
каждого чтения. `tests/check_rev13.py` обратимо нормализует **только**
конкретный проверенный блок REV41 перед исходным byte-exact hash-контрактом
FastbootProtocol (REV13 + REV29). Любое стороннее изменение исходника
по-прежнему должно проваливать guard.

Полная проверка — JVM, Android lint, сборка и установленные тесты API26/34.
Физический ответ старого fastbootd через OTG, отключение, многократные INFO,
отмена и фактическая длительность реакции ещё не измерены.
