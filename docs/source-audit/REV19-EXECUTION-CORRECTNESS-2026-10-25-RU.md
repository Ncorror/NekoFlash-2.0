### Fastboot

Поддерживаются `-s SERIAL` и `-sSERIAL`; регистр serial сохраняется. Повтор одинакового селектора допустим, конфликт двух разных serial — ошибка. `-S` остаётся отдельным параметром sparse, его нереализованность по-прежнему сообщается явно.

USB descriptor serial имеет приоритет. `getvar:serialno` используется только при недоступном descriptor, а не как способ проигнорировать несовпадение. Автоматическое переключение на другой аппарат не добавлялось: пользователь выбирает нужное устройство в USB-панели, затем повторяет команду.

Host-параметры больше не попадают в OEM/raw wire-команду. Кавычки и escape-последовательности OEM-аргументов сохраняются; `--` завершает разбор host-параметров. Проверка выполняется внутри уже принятой операции, поэтому проверка в парсере не может устареть до запуска передачи.

### Sideload

Последовательность автоматической проверки:

1. При подключении к Recovery читаются USB serial, `/proc/sys/kernel/random/boot_id`, длина и SHA-256 текущего `/tmp/recovery.log`. Изменившийся во время снимка или недоступный журнал не создаёт достоверную границу.
2. При фактическом допуске Sideload создаётся UUID и сохраняется маркер этой попытки. Граница используется один раз и только для совпадающего USB serial. Повторное нажатие при занятом исполнителе ничего не стирает.
3. `DONEDONE` или предусмотренное протоколом закрытие после почти полной передачи переводит результат в `VERIFY_PENDING`. Это не подтверждение установки. Ошибка/отмена очищает только маркер своей попытки.
4. После подключения того же аппарата в Recovery проверяются boot ID и хеш прежнего префикса журнала. Читаются только дописанные байты. Префикс и boot ID проверяются ещё раз после чтения, чтобы обнаружить смену/обрезку журнала.
5. Требуется одна распознаваемая новая сессия Sideload. Несколько установок, другой тип recovery-операции, старый статус до начала текущей сессии, отсутствие финального результата не превращаются в SUCCESS.
6. Финальный статус Recovery имеет приоритет над промежуточным выводом скрипта. Строки `script succeeded` и сообщение об установке OrangeFox сами по себе больше не подтверждают окончание установки.

Распознаются существующие маркеры TWRP/OrangeFox и приглашение AOSP Sideload; числовые префиксы времени AOSP убираются только для разбора текста. Временные метки не используются как доказательство свежести. Формат приглашения сверялся с [AOSP adb_install.cpp](https://android.googlesource.com/platform/bootable/recovery/+/ec63d564a86ad5b30f75aa307b4bd271f6a96a56/adb_install.cpp); финальные статусы — с [AOSP recovery.cpp](https://android.googlesource.com/platform/bootable/recovery/+/android-8.1.0_r2/recovery.cpp). Это проверки формата исходников, не совместимости всех recovery-сборок.

Прямая передача ZIP при первом подключении уже в режиме Sideload сохраняется. Если нет предыдущей границы Recovery, уникального serial, доступных shell-утилит, совпадающего boot ID/префикса или однозначной новой сессии, установка остаётся неподтверждённой — нужно посмотреть экран Recovery. Старые маркеры REV18 без UUID не мигрируют в доказательство успеха.

Лимит 512 KiB относится только к окну чтения диагностического текста, не к размеру ZIP. При превышении окна результат остаётся UNKNOWN. Сохранился часовой срок ожидания результата; он не прерывает передачу. После перезапуска процесса подтверждение пишется в диагностику, но не подменяет несвязанное состояние GUI.

### Native USBFS

JNI-сигнатура и формат результата сохранены. `hardTimeoutMs = 0` теперь валиден в Kotlin и C++; отрицательные значения и положительный общий deadline короче stall timeout отклоняются. Положительный общий deadline остаётся доступен API, но основной Fastboot-путь его не задаёт.

Контроль времени вынесен в небольшой C++ helper, который используется существующими submit/reap-проверками. Тест гоняет этот же helper по виртуальной 40-минутной передаче с прогрессом, остановке первого/следующего URB, положительному deadline и времени больше 32-битного диапазона. Это не реальная 40-минутная USB-передача. Отмена и управление памятью незавершённых URB не переписывались. Блокирующий `pread` по-прежнему нельзя прервать одним флагом отмены; проверка выполняется после его возврата.

## Что проверяем на разблокированном Poco X3 Pro

| Сценарий | Ожидаемый результат |
|---|---|
| Неверный `-s`, в том числе для flash/boot/erase/fetch/OEM | Пользовательская команда и DATA не отправляются; показывается несовпадение serial |
| Правильный `-s`; без `-s`; raw OEM с кавычками и `--` | Прежнее исполнение, корректный wire-текст |
| Recovery → Sideload → Recovery | Подтверждается только текущая распознаваемая попытка с совпадающим boot ID и префиксом |
| Два нажатия запуска во время Sideload | Второе отклоняется, UUID первой попытки сохраняется |
| Повтор той же ZIP, старый SUCCESS, другой аппарат той же модели | Нет ложного успешного результата |
| Смена boot ID, обрезка/ротация журнала, недоступный SHA-256 или serial | UNKNOWN/VERIFY_PENDING; передача ZIP не запрещается |
| Передача Native USBFS дольше 90 секунд с прогрессом | Нет обрыва по общей длительности |
| Реальный stall, отмена в разное время, отключение кабеля | Корректная ошибка/отмена, возврат URB или poison backend; следующая операция не стартует до безопасного завершения |

Эти строки — план аппаратной проверки, не отметки о её прохождении.

## Следующая работа и готовность

1. R04: надёжный владелец длительной операции, подтверждённый `startForeground`, восстановление статуса после закрытия UI/процесса.
2. R01: реальная host-семантика `format`, `-w`, `wipe-super`; текущие алиасы пока нельзя считать эквивалентом desktop fastboot.
3. R05/R09: большие RAW/sparse с учётом `max-download-size`, затем SAF-источники Mass Flash.
4. R06/R08/R10/R17: IME на устройствах, сохранение Quick Flash при пересоздании Activity, эффективное отображение длинной очереди и оставшиеся предупреждения lint.
5. R15/R16: аппаратная матрица, выпуск и проверка обновления подписанного APK.

Раскладка третьей вкладки остаётся утверждённым Sideload с двумя кнопками; новую структуру Settings этот пакет не вводит. Полный реестр остальных задач остаётся в REV18.

Ориентировочная готовность полного согласованного проекта остаётся **65–70%, техническая альфа**. Три дефекта исправлены на уровне кода, но отсутствие аппаратных испытаний и сервисного владельца операции не позволяет назвать сборку готовой к стабильному выпуску. Это инженерная оценка, не измеренное покрытие или вероятность успешной прошивки.
