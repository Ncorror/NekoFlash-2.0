## Что исправлено

В [аудите REV18](REV18-AUDIT-2026-10-25-RU.md) оставались два связанных дефекта:
R08 — Quick Flash терял выбранный файл вместе с Activity; R09 — очередь Mass Flash
могла исполнять только локальные File-источники. REV24 исправляет эти пути, сохраняя
существующие транспорт, foreground-сервис и потоковое разбиение образов REV23.

| До | После |
|---|---|
| Выбор Quick Flash жил в Activity | Метаданные хранятся в DeviceViewModel и атомарно сохраняются в приватном файле; новый экземпляр сессии повторно открывает источник |
| Сохранённый путь мог указывать на недоступный или изменившийся файл | Проверяются фактический размер, чтение первого/последнего байта и произвольный доступ; несовпадение размера требует повторного выбора |
| Mass Flash выбирал файл только из рабочей папки | Общий диалог предлагает «Файлы Android» или рабочую папку; в одной очереди допускаются file: и content: |
| Недоступность поздней строки выявлялась после предыдущих прошивок | Все источники проверяются на доступ, размер и seek до первого payload; перед каждым шагом размер проверяется повторно |
| Медленный ответ проверки мог примениться после нового выбора | Поколения запросов отбрасывают устаревшие результаты Quick Flash и очереди, включая удалённые строки |

Сохраняются только URI, отображаемое имя и подтверждённый размер. Файловые дескрипторы,
доступ к документу и разрешение запустить операцию не сериализуются. После восстановления
не начинается ни прошивка, ни автоматический повтор. Для запуска нужно отдельное нажатие.

Размер из метаданных document provider считается подсказкой: исходный размер фиксируется
по открытому дескриптору. Проверка не копирует целый образ во внутреннее хранилище.
Прежний путь resparse может создавать один временный пакет, как описано в REV23.
Потоки без seek и пустые/неизвестные по размеру документы отклоняются.

Проверка документов выполняется вне UI-потока. После выбора SAF приложение пытается
сохранить read grant; если provider не даёт постоянный доступ, это отражается в журнале,
а текущий доступ проверяется фактическим открытием. Сохранённый URI сам по себе доступ
не гарантирует. Целевой раздел открытого Mass Flash picker сохраняется в Bundle:
результат после пересоздания не подставляется в случайно выбранный другой раздел.

Порядок очереди, замена строки по точному имени раздела, явные суффиксы слотов и
отсутствие лимита 32 строки сохранены. Ошибка нового документа не удаляет прежнюю
валидную строку. Пока проверка добавления не закончилась, запуск очереди недоступен.
Ошибка предварительной проверки помечает соответствующий шаг и останавливает очередь.

## Интерфейс

Пять нижних вкладок, тёмная тема, оранжевый акцент, Sideload и Unlock сохранены.
Quick Flash показывает имя выбранного файла, состояние проверки или причину
недоступности. Кнопка запуска доступна после успешной проверки источника.
В очереди видны проверяемые разделы и ошибка добавления. Новые сообщения есть на RU/EN.

Визуальная проверка первого успешного API 34 выявила чёрный текст раздела/слота
на тёмном фоне и одинаковый вид включённой/отключённой кнопки Flash. Исправлены
выбранное значение и выпадающий список Quick/Mass Flash: светлый текст, тёмный popup,
стрелка раскрытия и элементы не ниже 48 dp. Подписи связаны с полями для доступности.
Кнопки запуска Quick/Mass используют отдельные состояния enabled/disabled:
оранжевая активная, приглушённая недоступная. Кнопки изначально отключены до привязки
состояния. Цветовая схема и расположение разделов сохранены.

Осмотрены восемь PNG из установленного приложения на эмуляторах **API 26 и 34,
320×640**: восстановленный выбор, состояние проверки/ошибки, выбор раздела и очередь
с SAF-документом. На обоих API видны читаемые значения и очередь; на API 34 также
подтверждены тёмный раскрытый список и итоговая ошибка с приглушённой кнопкой.
На API 26 `quick-partition-menu.png` снят до появления popup, а
`quick-unavailable.png` показывает промежуточное «Checking image». Эти два PNG
не считаются визуальным доказательством конечного состояния; требуется синхронизация
с отрисовкой в screenshot-helper. Runtime-assertions ошибки и отключения кнопки прошли
на обоих API. Проверка на физическом экране и с увеличенным шрифтом ещё впереди.

[Снимки и runtime-доказательства API 26](https://github.com/Ncorror/NekoFlash-2.0/actions/runs/40678433818/artifacts/12812126627),
[API 34](https://github.com/Ncorror/NekoFlash-2.0/actions/runs/40678433818/artifacts/12812276523)
хранятся до **27 ноября 2026 по Москве**.

Новые JVM-тесты проверяют атомарное сохранение, Unicode, повреждённую запись, смену
размера, удаление/возвращение файла, восстановление сессии без старта сервиса и
запоздавшие результаты проверки. Robolectric выполняет lifecycle-сценарии на API 26/34.
«Новая сессия» моделируется очисткой ViewModelStore и повторным чтением сохранённого
состояния; это не проверка принудительного завершения процесса на физическом устройстве.

Инструментальные тесты используют отдельный test-only ContentProvider через настоящий
Binder/FD: читают документ с неверной подсказкой размера, отклоняют pipe, проверяют
изменение размера, отказ provider и восстановление смешанной очереди. Отдельный сценарий
пересоздаёт настоящую MainActivity, проверяет файл, выбранные раздел/слот, цель открытого
picker, отсутствие запуска операции и отключение кнопки после удаления файла.
Provider входит только в AndroidTest APK, в production manifest его нет.

[Первый CI](https://github.com/Ncorror/NekoFlash-2.0/actions/runs/40569442221) прошёл 230 JVM-тестов, но оба Android-прогона завершились падением на
первом обращении к тестовому provider. Проверка DEX показала отсутствие Kotlin runtime
в отдельном AndroidTest APK: provider на Kotlin зависел от классов target APK,
недоступных его собственному процессу. Fixture переписан на Java/platform API;
CI теперь сохраняет logcat даже при падении тестового процесса. Новое замечание
UseKtx в FirmwareSelection исправлено без подавления lint.

Следующий прогон выполнил все 10 тестов на API 34, но API 26 остановился до тестов:
`adb logcat -c` не смог очистить журнал. Очистка/сбор диагностического logcat теперь
выполняются по возможности; обязательные проверки результата instrumentation,
четырёх PNG и независимого fsck не ослаблены. Итоговые результаты относятся к окончательному
прогону с этим исправлением и доработанным интерфейсом.
После визуального исправления полей/кнопок также убраны два новых XML-замечания:
используется compat-атрибут иконки, у строки popup нет лишнего собственного фона.

Отказ доступа в тесте моделируется самим provider. Выдача/отзыв постоянного системного
grant через DocumentsUI, перезагрузка телефона и сторонние облачные providers требуют
отдельной ручной проверки. Эмуляторные тесты не доказывают совместимость USB-прошивки.

## Что остаётся

- **R07 — следующий блок:** отмена и учёт места при импорте/распаковке APK/OBB,
  очистка незавершённого импорта; согласованный учёт временных sparse-пакетов.
  В `MainActivity.importFirmwareFile` нет проверки отмены внутри `copyTo` и перед
  публикацией; в `AdbProtocol.extractPackageArchiveContents` отмена проверяется
  между ZIP-записями, но не во время копирования одной большой APK/OBB-записи.
- **R08/R09:** реализация и автоматические проверки подготовлены; нужны реальные
  DocumentsUI/grants, несколько providers, перезагрузка и физическая USB-матрица.
- **R01/R04/R05/R15:** ARM/ARM64-хосты, bootloader/fastbootd, большие RAW/sparse,
  отмена в DATA, detach, фон и длительная передача.
- **R06/R10/R11/R17:** PTY/IME на телефоне, RecyclerView для длинных очередей,
  состояния Главной, оставшаяся локализация и lint-предупреждения; синхронизация
  screenshot-helper с отрисовкой API 26 и именование параметра тестового override.
- **R16:** интеграция серии веток, версия/SDK, постоянная подпись Release и обновление.

Проверка размера не доказывает неизменность содержимого: замену файла на другой
такой же длины она не обнаруживает. Между предварительным открытием и фактической
передачей источник может измениться; неизменяемый snapshot в этой ревизии не создаётся.
Ошибки чтения во время передачи останавливают выполнение, но уже записанные данные
не откатываются. Проверка всех строк до первого payload относится к доступу/seek/размеру;
полная проверка sparse и подготовка пакетов по-прежнему выполняются перед своим шагом.

Зависший системный вызов стороннего provider не обязан немедленно отвечать на отмену
корутины; устаревший результат будет отброшен, но принудительного прекращения любого
provider I/O здесь нет. Эти ограничения не скрываются за состоянием «файл выбран».

Готовность остаётся **около 80%, техническая альфа**. Это оценка оставшегося объёма,
не процент тестового покрытия. R08/R09 продвинулись, но физическая совместимость и
выпуск ещё не подтверждены. Команды записи на физическое USB-устройство не отправлялись.

## Первичный источник

[Android Developers — Storage Access Framework и сохранение доступа](https://developer.android.com/training/data-storage/shared/documents-files#persist-permissions).
Документация предупреждает, что даже persistable grant не сохраняет доступ после
перемещения или удаления документа. Поэтому восстановление метаданных сопровождается
фактическим открытием и проверкой источника.
