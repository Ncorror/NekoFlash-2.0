# NekoFlash 2.0 — REV20: сервис, жизненный цикл и восстановление статуса

Дата: 26 октября 2026. Репозиторий: **Ncorror/NekoFlash-2.0**.
База REV19: `763645e05b62a7a342b65d51e45c585761d5122d`.
Код REV20: `79bd57995d0482ecd568157c9321202433917962`.
[Draft PR #6](https://github.com/Ncorror/NekoFlash-2.0/pull/6) направлен в ветку REV19; в `main` эта серия не объединена.

Ревизия исправляет программную часть R04 из [аудита REV18](REV18-AUDIT-2026-10-25-RU.md). Устойчивость на физическом USB и при ограничениях питания конкретных прошивок остаётся непроверенной. IQ-HARRY7 добавлен в раздел **Developers** README со ссылкой на профиль.

## Что изменено

| Дефект | Исправление | Проверка |
|---|---|---|
| `viewModelScope` связывал исполнение с уничтожением владельца экрана | Операция имеет независимый lazy Job; общая USB-сессия принадлежит процессу и используется экраном/сервисом | Уничтожение и повторное создание тестовой Activity на API 26/34; отмена родительского UI scope |
| Ошибка запуска foreground могла оставить исполнение без сервиса | Тело операции начинается только после успешного `ServiceCompat.startForeground`; отказ/истечение ожидания завершают подготовку без команды | Отказ foreground в модели сервиса и через настоящий DeviceViewModel; повторный и запоздалый ACK |
| Запоздалые start/stop могли относиться к другой задаче | Один реестр активной операции и уникальный token в service intent; завершение проверяет тот же token | Отменённый запрос до/после запуска следующего задания, повторный ACK; таймаут следующей заявки завершает простаивающий сервис, старый callback не стирает новый результат |
| После гибели процесса статус и очередь терялись | Атомарный журнал последней операции и файл черновика в приватном каталоге приложения | Повторное открытие хранилища, повреждённые записи, порядок очереди, очистка черновика |
| Завершение сервиса могло выглядеть как пользовательская отмена | Отдельный результат `INTERRUPTED`; действующее двухфазное закрытие USB ждёт завершения Job, callback и native drain | Уничтожение сервиса при блокирующей работе не объявляет её завершённой до возврата |
| Фоновое уведомление не отражало полный жизненный цикл | Тихий текущий прогресс, итоговый статус, «Открыть»; итог можно смахнуть | Настоящий DeviceViewModel завершается с ошибкой отсутствующего устройства, уведомление теряет ongoing-флаг |
| UI callback Mi Unlock удерживал Activity | Слабая ссылка на экран и проверка его состояния перед обновлением | Анализ захватов callback; MiAccountClient/MiUnlockClient не изменены |

Сервис имеет тип `connectedDevice`, соответствующее manifest-разрешение и `stopWithTask=false`. `START_NOT_STICKY` и пустой реестр нового процесса исключают повтор команды из старого intent. В notification не добавлялась кнопка отмены.

При остановке сервиса сохраняется существующий порядок: запрос отмены → возврат блокирующей работы → подтверждённое освобождение URB → закрытие USB. Если безопасное освобождение не подтверждено, остаётся прежняя блокировка повторного подключения. Закрытие окна и смена вкладки эту остановку не вызывают.

## Что восстанавливается

- Сохраняются UUID, название, время начала, описание этапа, процент и итог последней операции. Начальные и конечные состояния записываются сразу; промежуточный прогресс — не чаще раза в секунду.
- Состояния `PREPARING` и `RUNNING` после нового запуска процесса переходят в `INTERRUPTED`. Даже 100% переданных байтов без финального результата не означают SUCCESS.
- Уже завершённые `SUCCESS`, `FAILED`, `CANCELLED`, `VERIFY_PENDING`, `INTERRUPTED` сохраняют смысл; повторное открытие не добавляет вложенные сообщения о прерывании.
- Сохраняется редактируемый черновик очереди с исходным порядком. Он не превращается в автоматически исполняемый план. Прямые SAF-источники Mass Flash остаются отдельной задачей R09.
- При обычном закрытии/открытии Activity в живом процессе сохраняется сама USB-сессия. После гибели процесса старые USB-дескрипторы и исполняющий Job не восстанавливаются.
- Если журнал повреждён, показывается неизвестный/прерванный результат; успех не придумывается. Если не удалось сохранить подготовку, передача не начинается. Ошибка записи конечного состояния отражается в журнале приложения; после следующего запуска может остаться консервативный статус «Прервана».

Это не обещание продолжить прошивку после force-stop, отключения питания или убийства процесса Android. Существующий wake lock имеет предел шесть часов; REV20 не меняет его и не подтверждает удержание CPU дольше этого срока. Реконструкция подробного списка шагов уже завершённой очереди не реализована: сохраняется черновик и последнее сводное состояние.

- Production package, версия `6.0.0-alpha11`, versionCode 234 и targetSdk34 не менялись. Собрана DEV-версия `.dev`; подписанный production Release в этой ревизии не выпускался.

Первый прогон обнаружил две проблемы тестов: Robolectric на API 26 не выдавал объявленное AndroidX signature-разрешение receiver, а одна проверка читала уведомление уже после завершения/удаления. Настройка тестов теперь сначала проверяет наличие и signature-уровень разрешения в объединённом manifest и только затем выдаёт его симулятору; notification проверяется во время контролируемой блокирующей операции. Production receiver не делался экспортируемым ради прохождения теста.

Robolectric моделирует framework API 26/34. Тестовая Activity проверяет владение общей сессией, но не воспроизводит всю разметку MainActivity, IME, физический USB или менеджер питания производителя. Тест с блокирующей работой использует latch, а не настоящий JNI/URB. Тесты хранилища моделируют перезапуск чтением записанного состояния, не убийством Android-процесса на устройстве.

## Аппаратная проверка перед выпуском

Испытания выполнять только на выделенном **разблокированном Poco X3 Pro**. Первые сценарии — на чтении/передаче тестового файла, не на записи раздела. Намеренное убийство процесса или выдёргивание кабеля во время реальной прошивки в этот план не входит.

| Сценарий | Ожидаемое поведение |
|---|---|
| Длительная операция → Home/смена вкладки/поворот | Выполнение продолжается, нет второго подключения, виден актуальный прогресс |
| Закрыть Activity/убрать задачу из recents → открыть приложение | Работающая операция и USB-сессия сохраняются, новый запуск не дублируется |
| Заблокировать экран, затем разблокировать | Реальная передача продолжается при доступном foreground execution; проверить ограничения MIUI |
| Отказ запуска foreground | Ошибка до начала пользовательской команды/DATA |
| Остановить процесс во время безопасного чтения → запустить приложение | «Прервана», черновик сохранён, команда автоматически не повторяется |
| Отключить кабель при безопасном чтении в фоне без Activity | Отмена/ошибка, корректное освобождение, никакого ложного SUCCESS |
| Завершение/ошибка/отмена | Итог совпадает в UI, журнале и уведомлении; итоговое уведомление можно убрать |
| Запрет уведомлений; увеличенный шрифт; RU/EN | Понятный статус в приложении, доступное действие открытия, отсутствие обрезанного текста |

Это план, не результаты выполненных испытаний. Проверки на физическом API 26, реальное OEM-ограничение фона, подписанный Release и обновление установленной версии ещё не выполнены.

## Дальнейшая работа и готовность

1. **R01:** точное поведение host-команд `format`, `-w`, `wipe-super`; сейчас некоторые алиасы не эквивалентны desktop fastboot.
2. **R05:** большие RAW/sparse с `max-download-size`, resparse/разбиение, отмена и stall на реальном USB.
3. **R09:** SAF URI/FD для каждого шага Mass Flash без обязательного копирования образа; стабильный открытый источник.
4. **R06/R08/R10/R11/R17:** IME/PTY на устройствах, восстановление Quick Flash, RecyclerView для длинной очереди, состояния Home, локализация и оставшийся lint.
5. **R04/R15/R16 — подтверждение на устройстве и выпуск:** аппаратная матрица, интеграция веток, подписанная сборка, проверка подписи и обновления.

Сохраняются утверждённые пять вкладок, тёмная тема с оранжевым акцентом и Sideload с двумя кнопками. Новая структура Settings не вводилась. Точный остальной реестр и границы — в REV18/REV19.

Готовность полного согласованного проекта — **около 70%, техническая альфа**. Это инженерная оценка объёма работ. R04 продвинут до проверенного программного решения; отсутствие аппаратной матрицы, полной host-семантики и больших образов пока исключает заявление о готовом стабильном релизе.
