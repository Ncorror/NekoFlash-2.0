# REV47 · зависший результат Sideload и восстановление экрана

Дата: 6 ноября 2026. Рабочая ветка: `fix/rev46-simple-tests-logs`, [PR #45](https://github.com/Ncorror/NekoFlash-2.0/pull/45).

## Симптом и причина

Автор сообщил, что табло оставалось после закрытия и остановки приложения; приложение было удалено. В коде `DeviceViewModel.restoreOperationState()` восстанавливает завершённый `VERIFY_PENDING` из `execution-state/last-operation.properties`. Это сохранённый неподтверждённый результат, а не доказательство продолжающейся передачи.

Первый фикс REV47 в `fc77cbff8b2b` скрывает старый результат при запуске без Bundle и добавляет 20-секундное автоскрытие нового `VERIFY_PENDING`. При проверке продолжения обнаружен дополнительный случай: после смерти процесса Android может восстановить Activity **с непустым Bundle**. Проверки `savedInstanceState == null` недостаточно.

## Исправление

Activity сохраняет идентификатор текущей диагностической/исполнительной сессии в Bundle. При создании экрана сравнивает его с идентификатором действующей сессии:

- та же сессия: обычное пересоздание Activity сохраняет активный прогресс и видимый новый результат;
- другая сессия либо отсутствие старого идентификатора: восстановленный завершённый результат скрывается в UI;
- активная операция остаётся видимой;
- новый `VERIFY_PENDING` скрывается через 20 секунд, `SUCCESS`/`CANCELLED` — через прежние 9 секунд;
- checkpoint, исходный verdict и диагностические логи не очищаются; `VERIFY_PENDING` не превращается в `SUCCESS`.

`DeviceViewModel`, ADB/Fastboot transport, сервис исполнения и алгоритмы записи не изменены этим дополнительным исправлением. Используется уже существующий идентификатор из диагностического snapshot.

При сверке исходного скриншота обнаружена пустая кнопка закрытия: стандартные горизонтальные отступы MaterialButton не оставляли места для крестика при ширине 32 dp. Убраны только внутренние отступы этой кнопки; размеры, цвета и композиция сохранены. Инструментальная проверка измеряет доступную ширину для символа и проверяет ручное закрытие/пересоздание.

Также проверен приложенный `reports.zip`: он содержит четыре USB-сессии в JSON/TXT (восемь файлов), без протокольного лога операций. Новый экспорт теперь включает `reports/usb-sessions` вместе с `logs` из известных публичного/приватного рабочих каталогов. Отдельная JVM-проверка сравнивает байты обоих видов журналов и исключает посторонние файлы. Наличие USB-снимка само по себе не доказывает успешную прошивку.

## Проверка

В `OperationResultRestoreAndroidTest` добавлены три инструментальных сценария с настоящим `MainActivity`, без USB и запуска команды:

1. Загрузка существующего `VERIFY_PENDING`, отсутствие старого табло до/после пересоздания; checkpoint сравнивается побайтно.
2. Активный прогресс виден после пересоздания Activity; после завершения новый pending-результат показывается и автоматически скрывается. Verdict и байты checkpoint остаются прежними.
3. Видимый pending-результат переживает обычное пересоздание. Затем между уничтожением старого экрана и созданием нового заменяется сессия, сохраняя Bundle Android. Черновик команды восстанавливается, старое табло скрывается, verdict и checkpoint сохранены.

Третий сценарий **моделирует** восстановление после смерти процесса; он не убивает процесс приложения/инструментального теста. Реальная остановка Android/OEM и физический Sideload требуют проверки на устройстве. Никакой успешный аппаратный результат здесь не заявляется.

Структурные проверки `tests/check_rev26.py`, локализация, документация, TestBook и правила CI проверяются локально; сборка/JVM/lint и 23 инструментальных сценария на каждом API 26/34 выполняются через GitHub Actions. Состояние нового коммита и доказательства доступны в PR; результаты предыдущего SHA не считаются результатами нового.
